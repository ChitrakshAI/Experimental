# Marketplace Hub

The operating system for Oraya / Hanflux AI's freelance-marketplace go-to-market. Fiverr today, Upwork next, more platforms after that.

It is a folder, a single Python file and an append-only ledger. No database, no dependencies, no install step. Python 3 standard library only, so it runs on a Mac with nothing set up.

---

## Why it exists

Marketplace work fails quietly in a specific way. Numbers get read and not written down. A gig gets edited on a hunch and nobody can say afterwards whether the edit helped. A verification form sits half-finished for three weeks because it is not on any list. A client's before numbers vanish the day the new system goes live. Six weeks in, the honest answer to "what is working" is "I think the second gig?"

So the hub holds three things and only three things:

1. **The registry.** Which accounts exist, on which platforms, owned by whom, in what state. `accounts.json`.
2. **The ledger.** Every action taken on any marketplace, appended, never edited. `ledger/events.jsonl` and `ledger/metrics.jsonl`.
3. **The playbooks.** How each repeated thing is done, written down once, so it is done the same way twice.

Everything the CLI prints is derived from those. There is no hidden state.

---

## The rule

**Every action on any marketplace gets logged.**

A gig saved, a gig published, a message answered, an order delivered, a blocker cleared, a dollar of ad spend, a review received. If it is not in the ledger, it did not happen.

Three properties follow from that, and they are the whole design:

- **Append-only.** Nothing is ever edited in place or deleted. A mistake is corrected by appending a correcting event. History is the point: the value is not today's snapshot, it is being able to say in November what actually changed in September.
- **Idempotent.** Re-running a command does not corrupt anything. An event with an explicit `--id` that already exists is skipped. An identical metric snapshot is skipped. A corrected snapshot is a new line and the reader takes the last one.
- **Plain text.** JSONL and markdown. Readable with `cat`, diffable in git, greppable, and still readable in five years without this tool.

## The daily 30 minutes

Same time every day. The order matters: gates first, because a listing that cannot publish has no ranking to optimise.

| Minutes | Do |
|---|---|
| 0 to 2 | `python3 hub.py status`. Read the open blockers and the overdue flags |
| 2 to 12 | Inbox. Every buyer message answered inside 60 minutes. This is a direct ranking input and it is the only lever that works from hour one |
| 12 to 22 | The numbers. `monitoring/daily-check.md`, then one `hub.py metrics add` per gig |
| 22 to 28 | One thing off the next-actions list. The top one, by due date, not the comfortable one |
| 28 to 30 | Log what you did. `hub.py log`. Close any blocker that cleared |

On the weekly slot, replace minutes 22 to 30 with `playbooks/weekly-review.md`, which takes 30 to 40 and is where decisions get made. The daily loop collects. The weekly loop decides. Keeping those apart is what stops a single noisy day from becoming a strategy change.

## Every command

Run everything from inside the folder.

```bash
cd marketplace-hub
python3 hub.py --help
```

### `status`

The dashboard. Per account: verification gates, every listing with its derived state, open blockers, next actions with overdue flags.

```bash
python3 hub.py status
python3 hub.py status --platform fiverr
```

Listing state is derived from the ledger, never stored. The states are `not-started`, `draft`, `pending-verification`, `live`, `paused`, `archived`, and the derivation is the last lifecycle action logged against that listing.

### `next`

The single next action per account. One line each, no list to triage.

```bash
python3 hub.py next
python3 hub.py next --platform upwork
```

The ranking is fixed and it is the whole point: an **overdue task** beats an **open blocker**, which beats the **next due task**, which beats the next unfinished step in the `STRATEGY.md` build order. Open blockers are themselves ranked so that a gate stopping a listing from publishing outranks a cosmetic gap, whatever order they were logged in, because a gig that cannot publish has no ranking to optimise.

When every blocker is closed, every task is done and every build step is logged, an account reads `CLEAR`, which means pull today's numbers and send today's proposals.

### `handoff`

Writes `NEXT-SESSION.md`: a complete resume brief for a fresh Claude session with no memory of this one.

```bash
python3 hub.py handoff
```

Account state, what is built, exactly where the browser work stopped and on which step, the gates only the user can clear, the open blockers and overdue tasks, the next action per account, the full status dump, and the first ten commands to run. Run it at the end of any session that touched a browser, and again at the end of any session that changed the plan.

### `log`

Append one event.

```bash
python3 hub.py log --platform fiverr --account hanfluxai --entity gig \
  --ref gig2 --action description_saved \
  --detail "pasted the description, 1,184 of 1,200 characters" \
  --actor chitraksh
```

| Flag | Meaning |
|---|---|
| `--platform` | `fiverr`, `upwork`, `meta`, `google`, `all` |
| `--account` | the handle, for example `hanfluxai` |
| `--entity` | `profile`, `gig`, `proposal`, `ad`, `order`, `review`, `message`, plus `account`, `task`, `blocker`, `campaign` |
| `--ref` | which one: `gig1`, `seller-profile`, `id-verification`, an order id |
| `--action` | what happened |
| `--detail` | one sentence of plain English |
| `--metric k=v` | repeatable numeric context |
| `--actor` | who did it. Defaults to `$HUB_ACTOR` or `chitraksh` |
| `--due` | for `--entity task`, a due date |
| `--id` | explicit id, so re-running the same command is a no-op |
| `--once` | skip if an identical event already exists, ignoring the timestamp |

**Actions that move state:** `draft_started`, `draft_saved`, `draft_complete`, `submitted_for_review`, `published`, `paused`, `unpaused`, `archived`, `not_started`. Anything else is recorded and leaves the state alone.

**Blockers** are `--entity blocker` with `--action opened` then later `closed`. **Next actions** are `--entity task` with `--action opened --due YYYY-MM-DD` then later `done`.

### `metrics add`

One daily snapshot.

```bash
python3 hub.py metrics add --platform fiverr --account hanfluxai --gig gig1 \
  --impressions 412 --clicks 9 --orders 0 --messages 2 \
  --response-time-h 0.4 --success-score 0 --source fiverr-gig-analytics
```

Fields, grouped the way the platforms group them. Every one is named in `monitoring/daily-check.md` with where it lives in the UI and what good looks like.

| Group | Flags |
|---|---|
| Fiverr gig analytics and seller dashboard | `--impressions --clicks --ctr --views --orders --conversion-rate --messages --response-rate --response-time-h --success-score --rating --cancellations --unique-clients --earnings-lifetime` |
| Upwork Stats and trends | `--profile-views --invitations --proposals-sent --proposals-viewed --interviews --hires --boosted-proposals --connects-spent --connects-balance --jss --earnings-12mo` |
| Pipeline input, counted by hand | `--jobs-identified` |
| Paid channels | `--ad-spend --ad-clicks --ad-impressions --ad-leads` |

CTR is computed from impressions and clicks when not supplied, and conversion rate from clicks and orders the same way, in both cases only when both sides were actually read.

Counters sum across a week. Rates and levels average, which is why `--connects-balance`, `--jss` and `--earnings-12mo` are averaged rather than added: summing seven daily readings of a balance is nonsense. **JSS displays every 14 days, so log it on change only.** Re-logging an unchanged figure daily turns one reading into fourteen and makes a stale number look like a measurement. Paid impressions are stored separately from organic ones, because summing them would quietly inflate the CTR denominator and make a bought impression look like a won one.

A snapshot is keyed on date, platform, account, gig and source. A repeat of an identical snapshot is skipped. A different snapshot for the same key is appended as a correction and the reader takes the last line, so **a correction must reuse the same `--source`**. **Leave a field off rather than guessing it.** An empty cell is a known unknown; a guessed number is a false reading that gets compared against next week.

### `metrics report`

Weekly rollup with week-over-week deltas and leading-indicator flags.

```bash
python3 hub.py metrics report
python3 hub.py metrics report --platform fiverr --gig gig1 --weeks 4
```

Counters sum across the week, rates and levels average. Upwork gets its own funnel table when Upwork rows exist, showing proposals sent, viewed, the view rate, interviews, the interview rate, hires, invitations, Connects and JSS in one line per week.

The flags at the bottom check the **seven ranked leading indicators** from `STRATEGY.md` section (i), in the research's own priority order: proposal view rate, interview rate against the 5% stop line and the 13% scale line, Fiverr CTR, response time and response rate, invitations, conversion rate, and qualifying jobs identified. Then the secondary reads: clicks without orders, messages without orders, Success Score against the level gates, rating, cancellations, JSS, ad spend without clicks, Connects without interviews, and over-boosting.

They are prompts, not verdicts. **"No flags fired" means no rule matched, not that everything is fine.**

### `checklist`

The launch checklist, with done and pending read from the ledger.

```bash
python3 hub.py checklist
```

Items tick themselves when the real event is logged. An item with no natural event can be ticked explicitly with `--entity task --action done --ref <key>`.

### `ads`

```bash
python3 hub.py ads list
python3 hub.py ads log --campaign fvr-promoted-gig1 --date 2026-10-02 \
  --spend 12.40 --clicks 7 --impressions 940
```

A campaign must exist in `ads/campaigns.json` before spend can be logged against it, so no dollar lands in the ledger without a named owner, a target and a stated hypothesis. Spend writes one row to `metrics.jsonl` and one event to `events.jsonl`, which is what puts cost per message in the same table as everything else.

### `export`

```bash
python3 hub.py export
python3 hub.py export --date 2026-10-12
```

Writes `reports/YYYY-MM-DD.md`: status, checklist, metrics with deltas, and the week's events. Commit it. Twelve of these in a row answer questions that no single one can.

## Adding a new account

1. Add a record to `accounts.json` on the existing platform: `platform`, `handle`, `owner`, `jurisdiction`, `status`, `purpose`, `tos_notes`, `created`, `verification_state`, and `gigs` or `profiles`.
2. Set `status` to `planned` until it exists, then `active`.
3. **Fill `tos_notes` honestly.** Quote the platform's own words, mark the note `VERIFIED` and cite the research section that carries the URL. If the rules have not been read, the note says `confirm multi-account rules before creating` and the account stays `planned`. Never assert a rule that has not been read. The Fiverr and Upwork notes in the registry are verified and quoted; the Fiverr agency record is marked `BLOCKED` with the reason, which is a different thing from unverified.
4. Log the creation: `--entity account --action created`.
5. Open a blocker for each verification gate, so `status` shows them until they clear.

## Adding a new platform

1. Add the account record as above, with the new `platform` value. No code change is needed: `status`, `log`, `metrics` and `export` are platform-agnostic by construction.
2. Write `playbooks/<platform>-<motion>.md`: the exact click path, the field limits, the interface quirks, the denial triggers. That file is the deliverable, not an afterthought.
3. Add templates under `templates/` for that platform's first contact.
4. Add any platform-specific metric to `METRIC_FIELDS` in `hub.py`, and to `SUM_FIELDS` or `AVG_FIELDS` so the weekly rollup knows whether to add it or average it.
5. Add a campaign channel to `ads/campaigns.json` if the platform has paid placement.
6. Add the platform's numbers to `monitoring/daily-check.md`.
7. Mark everything unverified as TODO. A TODO is a known gap. An invented number is a wrong answer that looks like a right one.

## Writing rules

These are not preferences. They are inherited from the project's locked writing rules and they apply to every file here and to every word sent to a buyer.

- **No em dashes. Ever.** The character U+2014 is banned from every file in this folder, from gig copy, from ad copy, from messages, and from text baked into images. Split the sentence, use a colon, or use a comma. Also banned as substitutes: the double hyphen, and a spaced hyphen or en dash used as a clause break. The one allowed dash is an en dash inside a numeric range.
- **Ship gate:** grep for U+2014 before anything ships, and confirm the count is zero.
- **Every number carries its measurement basis and the date it was read.** A target is never quoted as a result.
- **No fabricated metrics, no fake social proof, no invented client stories.** Anything that lives outside a folder that has actually been read stays out, however good it sounds.
- **Anonymise client data.** No client, dealership or agency is ever named in public copy.
- **Compliance framing is engineering, not legal advice.** Never imply US bar admission. Never imply insurance licensure.
- **No hype.** Confident engineer-lawyer. No superlatives, no emoji, no exclamation marks.

The ship gate. Run it from the repo root before anything ships. It is written in Python rather than as a grep pattern for two reasons: the character is referred to by code point, so the check never contains the character it forbids, and it behaves the same on a Mac as it does anywhere else, which BSD grep does not.

```bash
python3 - <<'PY'
import pathlib
BAD = {0x2014: "em dash", 0x2013: "en dash", 0x2012: "figure dash", 0x2015: "horizontal bar"}
hits = 0
for p in sorted(pathlib.Path("marketplace-hub").rglob("*")):
    if not p.is_file():
        continue
    try:
        text = p.read_text(encoding="utf-8")
    except Exception:
        continue
    for code, name in BAD.items():
        n = text.count(chr(code))
        if n:
            hits += n
            print("%s: %d %s" % (p, n, name))
print("total banned dash characters: %d" % hits)
PY
```

`total banned dash characters: 0` is the only acceptable result. Run the same check against any text baked into an image, including SVG labels and JavaScript template strings.
